## 3. Binding V1 product model and the pricing/fulfillment separation (D-RI-2)

Owner-confirmed V1 forms: **(A)** single scheduled session — already certified Booking; S6 adds check-in fulfillment where a product wants it. **(B)** finite multi-use package (5 massages, 10 Pilates visits) — purchase once, no upfront occurrence selection, `purchased → used → remaining`. **(C)** limited-use membership (8 boxing visits / 30 days) — finite usage + validity period. **(D)** unlimited time-based pass/membership (one month unlimited) — semantic mode, never a fake large counter. **(E)** recurring scheduled program (Mon/Wed boxing, academy term) — occurrences belong to the calendar; attendance recorded only on actual check-in. **(F)** automatic recurring billing — **NOT V1**; manual re-purchase only; no Stripe subscription machinery (docs/24 §14.B5 untouched).

**Vocabulary ruling applied (D-RI-2: pricing ≠ fulfillment).** The certified `program_price_option.kind` set `dropIn·monthly·term·camp·package·free` stays the *selling-shape* vocabulary. S6 proposes exactly ONE additive kind: **`membership`** — the docs/24 §2.6 model-ready extension — covering forms C and D (this revises docs/09 §21.14's pre-rebaseline ruling "monthly remains the membership representation"; D-RI-2 declared it ripe — §22 D-S6-3). Form B stays `package` (its certified `sessions_count` already carries the finite total and is publicly served). Forms A/E stay `dropIn`/`free` and `monthly`/`term` cohort enrolment on the certified Booking spine. **No fulfillment semantics enter the price enum**: finite/unlimited, validity, reservation-required, and walk-in live in a NEW per-price-option fulfillment configuration:

**`price_option_fulfillment`** (provider-editable product configuration; one row required per entitlement-producing option, i.e. kinds `package`/`membership`; forbidden for other kinds): `price_option_id` PK + composite FK `(price_option_id, program_id) → program_price_option (id, program_id)` · `program_id`, `organization_id` (org-composite FKs, the certified binding pattern) · `usage_kind ∈ {finite, unlimited}` (CHECK: `package` ⇒ `finite`; `membership` ⇒ either) · `uses_total integer` (CHECK: NOT NULL iff `finite` AND kind=`membership`; for `package` the certified `sessions_count` IS the total — no duplicate column, service-enforced consistency) · `validity_kind ∈ {daysFromPurchase, fixedEndDate, none}` · `validity_days integer` / `validity_end_date date` (paired CHECKs; `none` allowed only where explicitly configured — CHECK: `unlimited` ⇒ validity_kind ≠ `none`, an unlimited pass with no expiry is not a V1 product) · `reservation_required boolean NOT NULL` · `walk_in_allowed boolean NOT NULL` (CHECK: at least one true; both true is legal — a product may genuinely permit both) · optional `branch_id` (org-composite FK; NULL = valid at all provider branches — the smallest branch-limitation representation) · `created_at/updated_at/version`. **Shape:** `id` · `account_id` (purchaser) · `participant_id` + composite FK `(participant_id, account_id) → participant` (beneficiary; cross-account substitution structurally impossible — the certified 0013/0015 precedent) · `organization_id` · `program_id` (+ org-composite FK) · `price_option_id` (+ program-composite FK) · `offer_id?` · `quote_id NOT NULL → price_quote (id)` (the immutable commercial snapshot — `price_quote` is already append-only) · `state` · `reference_code` write-once UNIQUE (customer-facing, non-enumerable; own prefix, distinct from Booking's) · `expires_at timestamptz NOT NULL` (the purchase-window backstop — §5) · `confirmed_at?` · `created_at/updated_at/version`. **State machine (trigger-enforced, identity-frozen, the `booking` pattern):** `pending_payment → confirmed | expired | payment_failed`; `payment_failed → pending_payment`; `confirmed` terminal in V1 (no cancellation authority — §19). Exactly-one-result invariant: `entitlement.purchase_id UNIQUE NOT NULL` (§7) — one confirmed purchase yields exactly one entitlement, in the same confirming transaction.

**Quote authority:** entitlement purchases reuse `requestQuote`/`price_quote` verbatim except the unit anchor: `ck_price_quote_one_unit` widens additively to *exactly one unit for capacity option kinds; exactly zero units for entitlement option kinds (`package`, `membership`)*. **Free acquisition (owner §30):** if a provider's entitlement product genuinely quotes zero total, a bounded atomic **`confirmFreeEntitlementPurchase`** boundary (mirroring `confirmFreeBooking`: `runIdempotent` scope `entitlement.confirm.free`, refuse `total_fils ≠ 0`, create purchase + entitlement in one transaction) confirms WITHOUT any PaymentIntent — the certified `enforce_payment_intent_amount` trigger already refuses zero-total intents. ## 5. W5 payment-binding evolution — the exact additive invariant (D-RI-1 STOP item)

**Exact current constraint that blocks S6** (quoted from `0015_payment_foundation.sql`): `payment_intent.booking_id uuid NOT NULL` · `payment_intent.hold_id uuid NOT NULL` · `CONSTRAINT fk_payment_intent_booking FOREIGN KEY (booking_id, account_id, quote_id, hold_id) REFERENCES booking (id, account_id, quote_id, hold_id)` · `fk_payment_intent_hold → capacity_hold (id)` — plus upstream `ck_price_quote_one_unit` (§4) and `ck_booking_one_unit`. A unit-less paid purchase cannot produce a `payment_intent` today. Per the owner ruling, W5 gains a **canonical commercial-target abstraction**: a PaymentIntent pays for exactly one commercial target, which is EITHER a capacity Booking OR an EntitlementPurchase.

**Exact proposed additive model (migration `0017`, S6-1):**
1. `payment_intent.booking_id` and `payment_intent.hold_id` drop NOT NULL (columns, FKs, and composite FK retained verbatim).
2. New nullable `payment_intent.purchase_id uuid` + `CONSTRAINT fk_payment_intent_purchase FOREIGN KEY (purchase_id, account_id, quote_id) REFERENCES entitlement_purchase (id, account_id, quote_id)` — the same reciprocal-identity discipline as the Booking binding (account and quote provably shared with the target).
3. **Exactly-one-target invariant:** `CONSTRAINT ck_payment_intent_one_target CHECK (num_nonnulls(booking_id, purchase_id) = 1)` + pairing `CONSTRAINT ck_payment_intent_target_shape CHECK ((booking_id IS NULL) = (hold_id IS NULL))` — a Booking target always carries its hold; a purchase target never carries one.
4. Live/succeeded exclusivity mirrors: existing partial uniques `uq_payment_intent_live_booking`/`uq_payment_intent_succeeded_booking` keep working unchanged (NULLs excluded); add `uq_payment_intent_live_purchase ON (purchase_id) WHERE state IN ('created','in_progress')` and `uq_payment_intent_succeeded_purchase ON (purchase_id) WHERE state = 'succeeded'`.

**Backward compatibility for every W5 Booking invariant:** every existing `payment_intent` row has `booking_id`/`hold_id` NOT NULL in fact and satisfies both new CHECKs with zero rewrites; the composite Booking FK, amount-pinning trigger (`enforce_payment_intent_amount` reads `price_quote` via `quote_id` — target-agnostic), state machine trigger, idempotency-key uniqueness, and both Booking partial uniques are untouched; for Booking-targeted intents NOTHING changes at any layer. `enforce_economics_org_binding()` gains the purchase branch (org must equal `entitlement_purchase.organization_id` when the target is a purchase) — additive trigger amendment, Booking branch byte-equivalent.

**Saga/orchestration seam:** `startPaidCheckout` generalizes to a commercial target (same gates, same fail-closed `commissionTermsUnavailable`, same economics snapshot, same provider port); `runPaymentResultSaga.loadContext` dispatches on the target: Booking target → the existing certified path invoking **`confirmPaidBooking` unchanged** (same seam, same sole trusted caller, same HTTP-unreachability locks); purchase target → new **`confirmPaidEntitlementPurchase`** — *the entitlement-purchase success seam*: `runIdempotent` scope `entitlement.confirm.paid` under `principalRef 'system:payments'`, reciprocal check `intent.purchase_id/quote_id` against the purchase row, CAS purchase `pending_payment → confirmed`, INSERT the snapshotted `entitlement` (§7), audit + outbox — invoked ONLY by the saga, never imported by any `http/` module, added to the same source-lock family that pins `confirmPaidBooking`.

**Backstop semantics (replacing hold-TTL for unit-less sales):** `entitlement_purchase.expires_at` is an **abandonment wind-down window, not a fulfillment refusal**: a purchase holds no inventory, so late payment success does not need hold-death compensation — if capture arrives and entitlement creation is still legal, the saga confirms truthfully. The `sweepLapsedPaidCheckouts` analogue winds down only capture-less lapsed purchase intents (attempts → `errored/holdExpired`-analogous code, intent → `expired`, purchase → `expired`, provider `expireCheckout` best-effort). Recommended default window: 30 minutes, service-config like the hold TTL (no inventory pressure justifies the 10-minute severity; ratified with this plan). **Compensation (owner §29):** composed through the EXISTING W5 machinery, not cloned — when payment captured but entitlement creation cannot legally complete (participant archived, program/provider no longer sellable, purchase unconfirmable), the same ledger shape applies: capture posting without confirmation → same-amount `reversal`, intent → `failed`, purchase → `payment_failed`/`expired`, NO entitlement appears, NO settleable commission or provider payable (D-W5-7 settleable-vs-compensated projection generalizes over the target); `customerPaymentStatus` generalizes to purchase targets with the same converged vocabulary (`awaitingPayment/processing/confirmed/expired/compensationPending/compensated` — the D-RI-5 copy carries over to RI-4 unchanged). **No `package_payment`, no second intent model, no second Stripe flow, no second ledger exists anywhere in this design.**

## 7. Entitlement — participant-owned, snapshotted, finite/unlimited explicit

**`entitlement`** (append-only: `forbid_mutation` trigger + SELECT/INSERT-only grants — created complete at purchase confirmation, never edited): `id` · `purchase_id UNIQUE NOT NULL → entitlement_purchase (id)` (exactly one entitlement per purchase) · `account_id` · `participant_id` + composite FK `(participant_id, account_id)` — **structural participant ownership**: parent buys 10 swimming sessions for Ahmed → they are Ahmed's; cross-account AND cross-participant substitution are impossible by FK shape, and every redemption re-verifies the credential's participant against the entitlement row (no transferable/family package in V1) · `organization_id` · `program_id`, `price_option_id` (identity of what was sold) · **fulfillment snapshot** (copied VALUES, never references to the mutable config — later provider edits cannot rewrite sold terms): `usage_kind ∈ {finite, unlimited}` · `uses_total integer` (NOT NULL iff finite; from `sessions_count` for `package`, from config for `membership`) · `valid_from timestamptz NOT NULL` · `valid_until timestamptz` (NULL only for the explicitly-configured no-expiry finite case) · `reservation_required boolean` · `walk_in_allowed boolean` · `branch_id?` (branch limitation where the product had one) · schedule reference where the product is pattern-bound (`schedule_ids` snapshot for form-E-adjacent membership display — see §12) · `created_at`.

**Finite vs unlimited are explicit modes.** Finite truth: `remaining = uses_total − COUNT(attendance_record WHERE entitlement_id = …)` — **no mutable `uses_used` counter exists as authority**; writes serialize on the entitlement row lock (§10) and reads use the indexed aggregate; derived counters may appear in projections but history is always reconstructable (owner §11/§17). Unlimited: NO remaining value of any kind — no `999999`, no sentinel; attendance rows still record every visit. Effective status is DERIVED (the certified effective-hold-truth pattern): `active` (within validity, not exhausted) / `expired` (past `valid_until`) / `exhausted` (finite and fully used) — no state column, no sweep required for correctness; the final-use redemption emits `entitlement.exhausted` in-transaction because that transition IS authoritative (§15).

**Validity start (owner §9):** V1 rule — **validity begins at purchase confirmation** (`valid_from = confirmed_at`; `daysFromPurchase` ⇒ `valid_until = confirmed_at + days`; `fixedEndDate` ⇒ the configured date). Product docs are silent on activation modes; the smallest rule wins: no first-use activation, no explicit-activation mode in V1 (both remain additive extensions of `validity_kind` if ever wanted). Recommended as a ratified default (§22) rather than a blocking decision.

## 8. Reservation behavior (reservation-required / walk-in)

`reservation_required` and `walk_in_allowed` are independent booleans (≥ 1 true; both true legal — §3): the smallest representation of products that genuinely permit both. **Walk-in use:** credential generation while the entitlement is effectively active, the participant eligible, and product rules allow (§9); no occurrence needed. **Reservation-required use:** the customer reserves a future eligible occurrence AGAINST the entitlement through the certified capacity flow — zero-priced quote → hold → Booking (full capacity truth, no second reservation machinery), linked by the S6-3 subtype **`entitlement_reservation (booking_id PK → booking, entitlement_id → entitlement, org-composite)`** — the `enrolment`/subtype precedent. **Creating a reservation consumes NOTHING** (owner §10): only successful attendance/redemption consumes usage in V1; no-show consumption is deferred (§19). A reservation-linked check-in produces one attendance record referencing both the Booking (occurrence truth) and the entitlement (consumption truth). Service invariant: live reservations against a finite entitlement may not exceed `remaining` (checked under the entitlement lock at reservation time — overdraw-by-reservation impossible), while never counting as consumption.

## 9. Redemption credential — one-time, short-lived, QR-ready

**`redemption_credential`** (S6-2; state machine trigger, identity-frozen): `id uuid` (server-random opaque authority — never displayed; the future QR payload encodes an opaque server token, so QR arrives without domain redesign: the credential ROW is the authority, the rendering is presentation) · `display_code_hash` (the short numeric code the customer shows, stored HASHED — never plaintext at rest; owner-preferred numeric-first UI) · exactly-one-target: `entitlement_id?` / `booking_id?` (+ CHECK `num_nonnulls = 1`; booking target for scheduled check-in of form-A/E products, entitlement target for walk-in/flexible use) · `session_id?` (the occurrence, when scheduled) · `account_id`, `participant_id` (composite FK) · `organization_id`, `branch_id?` (provider/branch constraint scope) · `issued_at` · `expires_at` (**default TTL 10 minutes** — server config, owner-ratified) · `state ∈ {live, used, superseded, expired}` (`used` permanently terminal) · `used_at?`, `redeemed_by_staff_membership_id?` (+ org-composite FK) · `created_at/version`. Partial uniques: **at most one live credential per target** (`ON (entitlement_id) WHERE state='live' AND entitlement_id IS NOT NULL`, same for `booking_id`) and display-code liveness collision safety (`ON (organization_id, display_code_hash) WHERE state='live'`).

**Lifecycle rules (owner §13, binding):** issuing consumes nothing; expiry consumes nothing; after expiry the customer may generate again freely; successful use makes the credential permanently unusable (`used` + the `attendance_record.credential_id UNIQUE` backstop — §10). **Regeneration model — recommended: supersede-not-replay.** Issuing while a previous credential is still live atomically supersedes it (`live → superseded`) and mints a fresh code: exactly one live credential exists at any instant, a screenshot of an old code dies the moment a new one is minted, and "exactly one successful commercial/attendance effect" needs only the single-live invariant + row-level serialization — simpler and safer than replaying a possibly-compromised live code. Regenerate-vs-redeem races serialize on the credential row (proof 3, §17).

**Generation windows (owner §14):** scheduled targets — allowed from **60 minutes before to 60 minutes after** the occurrence start (server config per window side; ratified default); never days early. Walk-in/flexible entitlement targets — allowed while the entitlement is effectively active, the participant eligible, and remaining > 0 where finite (issuing still consumes nothing).

## 10. Atomic redemption + the attendance canonical model

**`attendance_record`** (S6-2; append-only: `forbid_mutation` + SELECT/INSERT-only grants — the mirror of `price_quote`/`enrolment` discipline; **never** a mutable `sessions_used += 1` counter as truth): `id` · `organization_id`, `branch_id?` · `participant_id`, `account_id` (composite FK) · `entitlement_id?` / `booking_id?` (≥ 1 present; both for reservation-linked check-ins — CHECK `num_nonnulls(entitlement_id, booking_id) >= 1`) · `session_id?` (scheduled occurrence where one exists) · **`credential_id NOT NULL UNIQUE → redemption_credential (id)`** (V1 attendance exists only through credential redemption; the UNIQUE is the structural same-code-twice impossibility) · `validated_by_staff_membership_id` + org-composite FK (the provider principal) · `occurred_at` (validation timestamp) · `source ∈ {numericCode, qr}` (only `numericCode` reachable in V1 — future QR compatibility without schema change) · `created_at`.

**Atomic redemption transaction (owner §16):** resolve the live credential by organization + code hash (or opaque token) → lock the credential row `FOR UPDATE` → verify: state `live`, unexpired, org matches, branch scope satisfied (staff scope AND credential/entitlement branch limitation), staff capability (§14) → lock the entitlement row `FOR UPDATE` where entitlement-targeted → verify effective validity + `remaining > 0` where finite (COUNT under the lock) → verify the scheduled window where session-bound → INSERT `attendance_record` → CAS credential `live → used` (+ `used_at`, staff id) → audit + outbox in-transaction. Two staff redeeming the same credential concurrently: the row lock serializes; the loser observes `used` and receives a typed refusal — **exactly one success** (proof 1). Two credentials racing the final finite use: the entitlement row lock serializes; the loser gets `entitlementExhausted` — **remaining can never go below zero** (proof 2). Lock order extends the certified global order: idempotency key → capacity unit → hold → booking → **credential → entitlement**.

**Corrections/fraud posture (owner §25):** V1 implements NO correction workflow; the append-only schema keeps audit-safe correction POSSIBLE — a future `attendance_correction`/reversal record can reference `attendance_record.id` append-only (never destructive deletion). docs/24 §3.5's `expected/no_show/excused` marking and the short-window mutable correction it described are superseded by this append-only design (§18); no-show semantics stay deferred with the owner as recorded.

## 11. `package_entitlement` — reconciled exactly, and superseded

Migration/compatibility plan: the table is empty (INSERT-grant-only with no inserting code since 0013), so `0017` drops it with no data movement; `db:verify` manifest, the S5-1 twelve-table lock, and the append-only-grant assertions are amended by the owning-slice pattern; docs/24's PackageEntitlement row is amended to record the supersession (§18). Down-migration recreates the empty structure verbatim.

## 12. Recurring scheduled products and the unified calendar (derived read — no second schedule truth)

**Entitlement validity ≠ calendar occurrences.** A Cobra Boxing monthly membership is: one entitlement active for one month + the program's existing **`recurring_schedule`** rows (Mon/Wed 19:00) as the pattern authority — `recurring_schedule` is certified as purely temporal and never owns inventory, so it is REUSED as the occurrence source for membership display; the entitlement snapshots the relevant `schedule_ids` (§7) for stable display. Missing a Monday consumes nothing and records nothing (owner §19). Where the provider generates Sessions from those schedules, real generated sessions (∩ validity) are the occurrences; otherwise read-time pattern expansion (weekdays/times/exceptions ∩ validity window) — never a materialized occurrence table.

**Calendar authority (owner §20):** a derived customer READ combining, at query time, per authoritative source: confirmed Session Bookings (`session.start_at/end_at`) · CampWeek bookings (date spans) · Enrolment/Cohort schedules (pattern expansion: `enrolment_cohort_schedule → recurring_schedule` ∩ cohort range, minus exceptions) · recurring scheduled membership/pass occurrences (above) · flexible-package reservations once actually booked (they are Bookings). **A purchased unscheduled 10-massage package contributes zero calendar dates.** Missing materialization: none needed — expansion is bounded by the queried range. Placement ruling: **the backend calendar read ships in S6-3** (`GET /customer/calendar?from&to`), so RI-5 is pure frontend consumption; S6 exposes the authority without duplicating state, and no `calendar_*` table exists. (docs/09 §13 calendar EXPORT — Apple/Google/ICS — remains W5-integration scope, untouched.)

## 16. Security/fraud model (designed against, explicitly)

Screenshot/shared code → 10-min TTL + supersede-on-regenerate (one live code; old screenshots die on regeneration) + single-use-forever. Brute-force/enumeration → codes are server-random, stored hashed, valid only while live (tiny live population per org), scoped to the validating org, and S6-2 adds service-layer attempt limiting per staff principal + org with typed lockout and audit on repeated failure — the design does NOT rest on "6 digits is probably enough": the numeric space is a human-convenience rendering over an opaque server credential, and code length is config (default 6) with the opaque-token path (QR) available without redesign. Cross-org redemption → credential rows carry `organization_id`; preview/redeem resolve ONLY within the caller's org (foreign codes are not-found-shaped). Branch bypass → staff `branch_scope` AND credential/entitlement `branch_id` both enforced in the redemption transaction (proof 5). Customer generating for someone else → participant/account composite FKs + not-found shaping (§13). Repeated same-code redemption → `used` terminal state + `attendance_record.credential_id UNIQUE`. Concurrent double redemption → row-lock serialization (proof 1). Expired-code replay → effective-expiry check under lock (proof 4). Client tampering with remaining balance → remaining is server-derived from append-only truth; no client value is ever accepted. Fake QR payload → V1 has no QR ingestion; the future QR path validates the opaque server token against the credential row (rendering ≠ authority).
